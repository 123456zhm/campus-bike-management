# 数据库设计草案

状态：讨论稿，尚未生成建表 SQL，未在 MySQL 中验证。基于 MySQL 8.0、InnoDB、utf8mb4 设计。

## 关系与职责

| 表 | 职责 | 主要关联与约束 |
|---|---|---|
| sys_user 等若依系统表 | 用户、角色、权限、日志 | 业务用户 ID 引用 sys_user.user_id；不再维护第二套用户 |
| bike_user_profile | 校园业务扩展和黑名单标记 | user_id 唯一关联用户；禁止在这里重复保存账号或密码 |
| bike_station | 站点、位置、启用状态 | 历史订单引用站点，关联记录存在时禁止物理删除 |
| bike_vehicle | 车辆编号、所属站点、状态 | 车辆编号唯一；状态：空闲、借出、维修、报废 |
| bike_billing_rule | 收费规则版本 | 记录计费单位、单价、生效时间；历史版本不可覆盖 |
| bike_rental_order | 借还订单、时间、费用及规则快照 | 引用用户、车辆、借还站点和规则版本 |
| bike_repair_order | 报修及处理状态 | 引用车辆、提交人；保存问题、状态与处理时间 |
| bike_repair_record | 工单处理过程 | 引用工单与操作人，记录状态变化和说明 |
| bike_bill | 应付、已付和账单状态 | order_id 唯一；用户归属通过订单确认 |
| bike_payment_record | 模拟支付流水 | 引用账单；设置业务请求号唯一，支持防重复 |
| bike_order_operation_log | 异常订单处理记录 | 引用订单与操作人，记录原因和处理结果 |
| bike_backup_record | 数据库备份执行记录 | 记录操作者、时间、状态和服务端文件位置 |

## 关键并发和历史规则

1. 借车事务按固定顺序锁定用户与车辆，检查账号、黑名单、欠费、用户进行中订单及车辆状态；条件更新空闲车辆成功后才生成订单。同一车辆和同一用户同时只能有一张进行中的订单。设计建表时评估 MySQL 8 生成列配合唯一索引作为第二道约束。
2. 还车事务锁定订单和车辆；校验当前用户与订单状态；写入费用快照、结束时间、还车站点和唯一账单，再根据未完成维修工单决定车辆状态。中途失败全部回滚。
3. 借用中的车辆提交报修时，订单仍可归还；归还时若故障尚未解除则改为维修。管理员处理工单与车辆状态时使用同样的车辆锁，禁止维修中车辆被借出。
4. 收费规则新增版本而不是覆盖历史含义；订单保存计算所需的生效规则快照、实际金额及结算时间。
5. 账单按订单唯一，支付记录按请求号唯一；模拟支付在锁定账单后校验金额及状态并写入流水。零元账单的状态应在建表和接口设计时明确。
6. 列表和报表分别按车辆编号、站点状态、用户和订单时间、车辆和订单状态、账单状态与支付时间设计组合索引，并依据实际查询复核。
7. 车辆归属在借出期间表示借车前最后所属站点；还车时更新为还车站点。站点当前在场车辆数仅统计未借出车辆；借出数量单独统计，避免将借出车辆误认为仍在站点。
